## 1. 研究定位与大论文边界

本小论文研究自然语言指令转换中的检索选择，以及效率与可靠性的权衡。拟采用流程：

```text
自然语言指令 + 当前任务状态 + 能力/规则版本
  → 选择检索策略
  → 组织相关规则与必要前置条件
  → 小型 LLM 生成任务 JSON
  → 独立程序校验
  → 传统规划器/固定执行接口
  → AirSim 执行与日志
```

检索模型候选为 BGE-M3 和 Qwen3-Embedding-0.6B；生成模型拟固定为 Qwen2.5-3B-Instruct。两者职责不同：Embedding 模型找规则，生成模型理解指令并产生 JSON。更换生成模型会引入额外变量，第一轮先固定生成模型。

| 项目 | 大论文主线 | 本小论文范围 |
|---|---|---|
| 研究对象 | 单机/双机目标感知、轨迹优化与任务分配等 | 自然语言任务转换与检索策略 |
| 方法重点 | 视觉感知、状态估计、运动规划与协同 | 规则检索、策略选择、结构化生成与校验 |
| 主要指标 | 感知、轨迹、运动与任务指标 | 规则覆盖、语义正确、误接受/误拒绝、延迟与资源 |
| 共享基础 | AirSim、已保存地图、传统规划器与现有控制接口 | 通过冻结版本引用同一平台基础 |
| 数据管理 | 保留现有目录和实验登记 | 新数据、配置、日志、分析、稿件保存于本目录 |

## 3. 核心研究问题

**总问题：在单卡资源受限的无人机仿真系统中，检索策略选择能否降低自然语言任务转换的成本，同时保持指令理解正确性和执行合法性？**

| 编号 | 研究问题 | 需要的证据 |
|---|---|---|
| RQ1 | 不同检索模型与模式，对必要规则覆盖和任务转换正确率有何影响？ | 同一指令、规则库、生成模型下的配对比较 |
| RQ2 | 检索额外耗时是否被较短的生成上下文抵消？ | 编码、搜索、上下文处理、生成和校验分段计时 |
| RQ3 | 根据指令特点选择无检索、稠密或混合检索，能否改善效率与可靠性的权衡？ | 固定策略、自适应策略、简单启发式之间的比较 |
| RQ4 | 独立校验对不可执行指令的误接受有多大影响，是否增加合法指令误拒绝？ | 候选输出与校验后决策分别评分 |
| RQ5 | 模型驻留和 AirSim 并发负载如何改变整体响应时间与资源占用？ | 冷/热启动与隔离/并发条件分别记录 |

主要问题为 RQ1—RQ3；RQ4、RQ5作为可靠性和工程代价分析，避免把所有模块都包装成新算法。

待检验假设：混合检索可能对具体词项更有帮助，稠密检索可能对口语改写更有帮助；小规则库可能直接提供完整规则更有效率。自适应选择是否有效完全由实验决定。以上均不能提前写成结论。

## 5. 候选方法：选择检索方式，再统一生成与校验

### 5.1 规则库

规则按可执行能力、动作语义、前置条件、参数约束、拒绝条件和少量开发示例组织。每张卡建议包含：

```text
rule_id、rule_version、scene_id、vehicle_id、action
rule_type、preconditions、parameter_constraints
text、source_pointer、review_status、validity
```

库中保存稳定规则；当前阶段、位置和实时状态作为每次请求的输入。检索库需独立于正式测试指令，不能把测试原句或答案作为示例入库。

元数据关联应帮助找到适用规则，同时保留用户请求动作的禁止条件。例如 READY 状态下请求 resume，应仍提供 resume 需要 PAUSED 的前置条件，不能因“不适用”直接过滤到查无此动作。

必要硬约束始终交给程序校验，不依赖 top-k 是否召回。模型输出的规则编号仅用于分析，不能作为执行授权。

### 5.2 检索模式

- BGE-M3 稠密：语义向量检索。
- BGE-M3 学习式稀疏：模型产生的词项权重检索。
- BGE-M3 稠密＋学习式稀疏：融合两路候选。
- Qwen3-Embedding-0.6B 稠密：按官方查询指令与编码方式使用。
- Qwen3 稠密＋BM25：外接词项检索后融合；其稀疏来源与 BGE-M3 不同。
- BM25：独立的低复杂度词项检索基线。

Qwen3 与 Gemma2 官方使用方式提供稠密向量 [4, 5]，不能把 BGE-M3 的原生稀疏模式直接套给它们。第一轮暂不加入 ColBERT 和重排模型，以控制变量和工作量。

### 5.3 自适应选择的最小候选

选择器先用可记录的特征，例如是否包含明确动作词、设备标识、口语改写及多重要求，选择“完整规则直接输入”“稠密”“混合”之一。复杂歧义和冲突不因选择器判断而自动解除，仍由生成、澄清或拒绝流程处理。

第一版优先使用简单可解释规则。阈值与融合参数只在开发集调整；每次选择都记录特征、分支、耗时和原因。不能用测试答案决定分支。查询“复杂度”分类也需要检查误判，不能假定分类正确。

选择器如使用额外模型，其调用、资源和延迟必须加入总成本。先导后再决定是否值得增加学习式选择器。不给方法预先冠以“最优”“实时”或“可靠”结论。

### 5.4 统一生成与校验

第一轮保持同一生成模型、JSON schema、必要的公共约束和独立校验。语义正确与程序通过是两个指标：现有字段和参数检查不能证明输出忠实于用户原意，必须与人工确认的标签比较。

状态校验在候选审批及执行接口处分别考虑；任务配置、规则版本或相关状态变化后应重新校验。若后续加入排队执行，需要评估命令被消费时的状态，不把生成时通过当作永久有效。

初始实验不加入反馈重试，先隔离检索选择的影响。若后续研究反馈修正，最多一次，增加相同调用预算的普通重试基线；修正不能擅自更改用户对象、数字、动作或顺序来让非法任务通过。

## 6. 实验设计

### 6.1 按阶段控制比较规模

**阶段 A：当前五动作先导。** 检查规则、标签、计时和接口是否可用，观察是否确有检索需求。若完整规则提示词已短且准确，不为制造优势填充无关规则。

**阶段 B：固定检索方案比较。** 建议七组：

| 组别 | 检索方案 | 目的 |
|---|---|---|
| B0 | 完整有效规则直接输入，不检索 | 检查 RAG 必要性；直接输入也包含真实前置条件 |
| B1 | BM25 | 低复杂度词项基线 |
| B2 | BGE-M3 稠密 | 主模型语义基线 |
| B3 | BGE-M3 学习式稀疏 | 分离稀疏通道贡献 |
| B4 | BGE-M3 稠密＋学习式稀疏 | 检验混合收益 |
| B5 | Qwen3-Embedding-0.6B 稠密 | 替代编码模型对照 |
| B6 | Qwen3 稠密＋BM25 | 替代混合方案对照 |

**阶段 C：策略选择。** 从阶段 B 的开发集结果冻结候选通道，比较固定稠密、固定混合、简单动作词分支及完整自适应选择。测试集只在策略冻结后用于最终比较。

**阶段 D：机制消融。** 保持编码模型不变，去掉状态/版本关联或固定所有请求走同一通道，判断收益来自哪一部分。程序校验的消融通过离线输出或状态回放评估，未经校验的候选不发送飞行指令。

**阶段 E：AirSim 与资源验证。** 先并发运行但不飞行，再按正式批准的协议做少量代表性执行验证。把解释正确、合法接受、任务实际完成分别记录；飞行成功不能反向证明所有语言条件都正确。

Gemma2 约 9B [5]，与两个约 0.6B 候选的资源规模不同。暂不列为必须完成组；如以后使用远程、更大显存或量化部署，单列扩展实验，披露精度、硬件及网络条件。

### 6.2 可比性约束

- 相同规则内容、分块版本、生成模型、JSON schema、基本推理参数和评分标准。
- 不同 Embedding 模型各自编码全部规则并重建索引；不同模型的查询与文档向量不混用。
- 按官方建议处理查询指令、归一化等 [3—5]，记录具体实现和模型版本。
- 第一轮以相同精度和设备条件做控制比较；量化或 CPU/GPU 分担作为另一个部署比较，不混为纯模型效果。
- 检索组统一候选数与最大上下文预算，并记录实际 token 数；完整规则基线如超过共同预算，应报告并另做实际部署条件比较，不静默截断。
- 融合方式、权重、top-k、向量维度和选择阈值在开发集确定并冻结。第一轮优先一种融合方式，避免大规模调参后只报告最优值。
- 文档向量离线预计算。分别记录离线建库成本、在线查询编码、索引搜索、融合与生成成本。
- 固定规则库时，输出维度可减少索引存储或搜索成本，但不预设它会同比减少编码模型耗时。

## 7. 指令数据与标注

### 7.1 标签分层

每条样本包含原句、来源、场景、当前阶段、规则版本，以及至少以下人工核对标签：

1. 语言含义：动作、对象、目标、显式数字、是否歧义/矛盾/复合要求。
2. 能力范围：当前系统是否支持请求。
3. 当前可执行性：动作前置条件与状态是否满足。
4. 预期处理：执行候选、澄清或拒绝；保留具体原因。
5. 必要规则集合：必须覆盖哪些 rule_id，包括禁止条件。

现有 JSON 的 ACCEPT 表示解析候选，最终状态是否合法由后续 dispatch 决定。数据中应单列这两层标签，不能把“语义识别正确但状态不合法”全部混成模型理解失败。

### 7.2 覆盖类型

| 类型 | 例子/关注点 |
|---|---|
| 明确命令 | 开始、暂停、继续、停止、返航 |
| 口语改写 | 先别往前了，悬停一下；结合约定的 pause/stop 区别评分 |
| 否定与修正 | 别返航；不是停止，是暂停 |
| 设备或目标约束 | DroneA、DroneB、另一个气球、未指明飞机 |
| 数字与单位 | 预设值、不同值、单位换算、数字遗漏 |
| 歧义或缺少动作 | 就这样吧；先停一下但未明确暂停/终止语义 |
| 冲突和复合要求 | 暂停后立即返航；合法动作附带不支持的要求 |
| 状态不满足 | READY 时继续，运行中再次开始 |
| 状态/规则变化 | 生成期间阶段改变、候选审批后任务版本变化 |
| 规则诱导与无关内容 | 要求忽略检查、越过当前能力或输出额外字段 |

上述例子是设计候选，当前不是已审核正式标签。

### 7.3 规模与划分建议

建议先导约 30—50 条，仅用于发现接口、标签和计时问题；开发集约 100—150 条；独立留出集初步预算约 300 条。具体数量在先导后根据类别、预期误差率和资源调整，正式测试前冻结。

同一原始指令的改写、同一冲突模板及其扩展保持在同一划分组。开发示例与测试原句不重叠；旧 smoke_eval 已被看过，不充当留出集。建议由作者审核全部正式标签，条件允许时增加第二位审核者并保存分歧及裁决。

AI 可辅助提出候选表达，但应保留来源，不能把模型答案直接当真值。测试模板数量、独立场景组数量和原句来源必须同时报告，不能仅靠大量近似改写增大样本量。

语义解析和状态回放可以覆盖不支持的请求，但不能声称这些能力已经在 AirSim 实现。扩充可执行任务需独立实现和验收，再升级能力版本。

## 8. 指标、计时与统计

### 8.1 可靠性

| 指标 | 定义/用途 |
|---|---|
| 必要规则覆盖率 | 按人工必要规则集合计算召回；多条规则时报告全部覆盖比例 |
| 检索排序质量 | 相关性标签允许时报告 Recall@k、MRR 或 nDCG；不只看 Top-1 |
| JSON 完整合法率 | 结构、枚举、字段和完整输出检查 |
| 语义完全正确率 | 关键动作、对象、目标、显式数值及预期处理均匹配标签；reason 不按字符串逐字匹配 |
| 不可执行指令误接受率 | 不可执行样本中，最终被接受执行的比例；单列能力越界、状态冲突等 |
| 合法指令误拒绝率 | 合法且清楚的样本中，被拒绝或不必要澄清的比例 |
| 澄清处理正确率 | 对真正歧义指令是否合理澄清，并记录过度澄清 |
| AirSim 执行结果 | 仅统计本论文真实发出且登记的任务会话，失败和中断独立保留 |

所有错误率都列分子、分母和对应样本类别。零观察错误不等于零风险，应报告置信区间。不能靠全部拒绝来获得低误接受率。

### 8.2 效率

在线总延迟按同一计时器定义：

```text
T_total = T_route + T_query_encode + T_search + T_fusion
        + T_context_build + T_llm_request + T_validate
```

无检索分支的对应项为零。LLM 请求内部可在运行时提供计时字段时拆分加载、输入处理与输出生成；与主机总耗时核对，避免重复相加。GPU 计时采用正确同步或设备事件，避免只测异步调用提交时间。

报告中位数、p95、失败/超时比例，以及输入/输出 token 数。分别报告全部请求、语义正确请求和正确可执行请求的延迟，避免方法通过快速失败显得更快。统计合法命令的正确响应和非法命令的正确拒绝时分别列出。

记录峰值显存、进程内存、系统可用内存、模型加载状态、CPU/GPU 使用方式和 AirSim 场景负载。检索速度与生成速度分开，主结论以用户实际等待的整体响应时间为准。

### 8.3 条件与统计单位

- 冷启动单列加载成本，模型驻留后的请求单列；明确预热次数和驻留策略。
- 先隔离测量，再测 AirSim 并发；记录地图、渲染/帧率限制、分辨率及其他进程。
- 正式批次使用固定随机种子安排方法顺序，跨批次平衡顺序，减少温度、缓存和背景负载影响。
- 同一输入在不同方法下配对比较。延迟可重复采样，但重复次数不算新增独立指令。
- 正确率和延迟报告配对差异及置信区间；存在模板簇时按指令组做聚类重采样，AirSim 按独立会话分析。
- 主要比较预先指定“自适应策略 vs 固定混合”，其他模型比较作为次要或探索性结果；多个比较需披露并酌情校正。
- “保持正确率”不能仅凭差异不显著得出。若采用非劣效判断，需在正式测试前说明可接受差距及样本量依据；当前未设定该阈值。
