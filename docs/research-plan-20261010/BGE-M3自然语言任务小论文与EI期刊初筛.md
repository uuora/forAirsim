# BGE-M3 自然语言无人机任务小论文与 EI 期刊初筛

核查日期：2026-10-10。用户要求：学校认可优先，EI 期刊及以上，中英文不限。本文是选题与投稿初筛，不是已完成实验的论文，也不是学校认可证明。期刊索引依据为出版社/期刊官方页面；未独立逐刊核对 Engineering Village 当期来源清单。最终单篇收录以数据库记录和学校口径为准。

## 1. 可行性与拟题

可以形成一个范围较小的实验研究，但贡献需要落在任务转换的正确性、约束遵循及资源成本上。选用 BGE-M3、LLM 和 AirSim 本身不是足够的创新依据。

建议工作题名：**面向已知地图无人机任务的检索增强自然语言指令转换与约束校验**。

拟研究问题：在固定小型语言模型及执行器的条件下，检索任务能力与场景规则，能否改善未见指令的正确转换？独立约束检查能拦截多少不可执行计划，其延迟及误拒绝代价如何？这是待检验问题，尚无收益结论。

拟流程：

```text
中文指令 + 当前任务状态
  → BGE-M3 检索能力、任务规则与合法示例
  → 小型 LLM 生成受限 JSON 任务候选
  → 独立程序校验完整有效配置、权限、参数与状态前置条件
  → 合法任务交给既有规划器与执行器
  → AirSim 采集执行、失败、时序及资源证据
```

关键约束须由程序从完整、有效配置读取，不能依赖 top-k 检索恰好命中。BGE-M3 的相似度也不是任务正确性或可执行性的证明。它支持稠密、稀疏、多向量检索，输入上限为8192 tokens；初始实验可以只用稠密检索，再决定是否增加混合检索。[官方模型说明](https://bge-model.com/bge/bge_m3.html)

## 2. 现有项目能提供什么

- `python/fixed_map_language.py` 已提供受限 JSON、开始/暂停/继续/停止/返航动作、ACCEPT/CLARIFY/UNSUPPORTED 分类及独立校验。默认本地 Qwen3 0.6B 的请求指定 CPU、两个线程、调用后卸载。
- `python/fixed_map_mission.py` 已有统一任务提交与执行接口。当前固定任务使用已保存地图中的已知目标位置，并不是从自然语言识别未知物体的位置。
- `reports/step2_perception_20261010/ACCEPTANCE.md` 明确当前指定目标尚无在线正例，不能把这个感知预览阶段写成已完成飞行闭环。
- 先前 AirSim、检测与控制记录可用于交代平台开发；不能混算为新增 BGE-M3 方法的成功率。源码与实验版本应单独冻结。

上述判断依据本地源代码与验收记录。当前没有 BGE-M3 的接入、检索比较或自然语言任务正式评测结果。

如果只研究目前五种固定按钮动作，完整规则提示很短，检索未必有必要。应先用“全部有效规则直接提供给同一模型”检验这一点；只有明确的任务能力、场景规则、参数或约束组合使知识选择成为问题时，才有充分理由引入检索。扩展任务必须同步实现和验证执行接口，不能只让 LLM 生成系统不会执行的动作。

## 4. 实验准备与比较

先开展小规模先导，再依据误差与成本估计正式样本量。可以以200–300条分层指令作为开发起点，数量不是期刊要求或充分性的保证。

指令应包括明确可行、同义改写、否定与顺序、多约束、歧义、当前能力不支持及当前状态不可行等情况。标注至少包含意图、目标/参数、有效约束和正确处理方式。任务模板与约束组合分组划分开发集和测试集；相近改写不要同时出现在知识库示例与测试集中。若使用模型辅助生成指令，需保存生成来源并人工复核，明确披露。

建议方法对照：

| 条件 | 目的 |
|---|---|
| 当前固定规则/接口基线 | 检验现有简单系统的表现 |
| 同一LLM、不检索 | 测量检索相对于基础模型的影响 |
| 同一LLM、全部有效规则提示 | 检验检索是否只是解决不必要的知识选择；记录其完整token成本 |
| BM25 + 同一LLM | 区分检索本身与BGE-M3语义检索的影响 |
| BGE-M3稠密检索 + 同一LLM | 拟方法基础版本 |
| BGE-M3混合检索 + 同一LLM（可选） | 检验关键词与语义匹配是否互补 |

检索条件使用同一知识库、相同检索条数与上下文预算，固定LLM版本、量化、提示格式和生成参数。全量规则条件的token成本单独报告。对校验器进行离线消融，保持其他条件不变；不可执行计划不必实际飞行，保存其候选和独立判定即可。

核心指标：规则 Recall@k、任务字段/意图正确率、首次候选约束违反率、JSON可解析率、可行任务完成率、不可行任务误接受率、可行任务误拒绝率、澄清正确率、修复次数、端到端p50/p95延迟、显存/内存峰值及仿真帧率。

将生成正确、校验通过和仿真完成分开统计。可行任务完成率分母包含拒绝、超时和失败；不可行任务单独报告合理拒绝率。不能通过全部拒绝宣称系统成功。指令与会话是不同分析单位；同一会话中的多帧不是独立重复。正式比较应使用相同场景/种子进行配对，报告不确定性，并按任务模板或会话处理相关性。

RTX3070 8GB条件下，先离线编码规则知识库，飞行期间按任务低频调用检索与LLM。显存是否足够、感知时效是否满足均需新增资源实测；当前硬件快照不能代替方法性能数据。

## 7. 改进方案：状态约束检索与有限反馈修正

本节为2026-10-10后续方法建议，尚未实现或验证。优先研究两项机制：在有效规则范围内进行状态相关检索，以及在不改变用户要求的前提下利用校验反馈修复转换错误。版本与状态绑定是二者的执行条件。任务JSON、低层规划与控制复用现有平台，新增模型训练不作为第一阶段要求。

### 7.1 将规则整理为可计算的条目

每条规则保存rule_id、scene_id、vehicle_id、version、适用状态、可用动作、参数及文本描述。机器字段来自受控配置，BGE-M3编码其文本描述和合法示例。先按有效版本、场景与权限筛选候选；状态、动作前置条件和参数冲突还应以独立程序计算。必要的硬约束完整保留，不以相关性分数决定是否校验。用户请求一个当前不可行动作时，应保留并解释对应前置条件，不能因为状态过滤把解释冲突所需规则一起丢掉。

例：“继续任务”在PAUSED状态可以对应resume，在APPROACH状态则不能重复resume。同一指令对应不同状态，给检索器和LLM的状态信息、处理方式及最终检查都应一致。状态感知不能仅体现在检索query增加一句文字；需要记录实际候选过滤、命中的规则及其适用性。

### 7.2 区分转换错误与请求本身不可行

将校验结果从一个自由文本异常整理为结构化错误：JSON_SCHEMA_ERROR、REQUEST_PLAN_MISMATCH、TARGET_AMBIGUOUS、PARAMETER_CONFLICT、ACTION_PRECONDITION_FAILED、RULE_VERSION_EXPIRED等，并绑定候选、规则ID及状态快照。具体枚举是拟设计，不是当前实现。

只有可在保持用户意图、动作、目标、参数及顺序的情况下修正的转换错误进入修复回路。把原始请求、首次JSON、相关有效规则及错误反馈发给同一LLM，最多修复一次；再次失败则不提交执行。还需同样调用次数的普通重试基线，以区分结构化反馈的作用与额外一次模型调用的作用。

若用户明确要求DroneA而候选写成DroneB，可以尝试纠正错误绑定。若用户明确要求超过上限的速度，不能把速度降到上限后报告任务被正确执行；应报告冲突并拒绝或请求用户澄清。两个目标都可能匹配时，也不能让修复模型随意挑选。模型声明的ACCEPT及规则引用不构成语义正确证明，语义保持需要独立标注和评测。

### 7.3 绑定版本、状态及执行前复核

候选计划记录规则版本、任务配置摘要和状态快照ID。rule_id仅用于追踪，校验程序必须核对其实际内容、版本和适用条件。解析时合法不意味着稍后执行仍合法；在执行器消费请求前读取最新状态，重新检查动作前置条件、配置版本与规划条件。发生版本或相关状态变化时使候选失效，不以旧审批继续执行。当前人工预览确认流程仍保留。

这适合形成具体测试：在生成期间更新规则版本、改变任务阶段，或使地图配置失效，观察系统是否错误接受旧计划及误拒绝仍可行计划。轨迹规划器仍负责几何可行性；本方案不声称检索器拥有物理安全保证。

### 7.4 用消融检验机制，而不是只比较模型名称

| 对照 | 受控差异 | 应回答的问题 |
|---|---|---|
| 全量有效规则提示 vs 普通BGE-M3检索 | 知识选取方式；全部条件获取同一当前状态并使用相同完整校验器 | 检索是否有必要，是否节约上下文而保持正确性 |
| 普通BGE-M3检索 vs 状态约束检索 | 候选适用性筛选与组装；同样的检索条数和上下文预算 | 过滤是否减少无效规则干扰、是否丢失解释冲突所需规则 |
| 单次生成 vs 相同预算普通重试 vs 一次反馈修正 | 是否重试、是否提供结构化错误信息 | 提升来自反馈内容还是多一次调用 |
| 解析时校验 vs 执行前再次校验 | 最新相关状态与规则版本的复核；移除条件只离线评测 | 是否减少陈旧计划的误接受，误拒绝和延迟代价如何 |

全部主比较保持同一LLM、JSON格式、有效规则库、任务集、解码设置及低层执行器。先保留现有五种动作做机制先导；如果知识库很小，全量提示效果相同或更好，应如实报告。正式多任务研究还需要增加并验证确实可执行的任务能力，不能通过塞入无关文档制造检索优势。

实验重点包括：同义与否定指令、意图/参数冲突、歧义目标、不同任务阶段、规则版本变化和生成后状态变化。先离线比较，确认合法输出再做AirSim独立会话验证。报告首次正确率、修复后正确率、不可行请求误接受率、可行请求误拒绝率、过期计划误接受率和p95延迟；状态改变后的合法性以执行前真实有效条件为判据。

### 7.5 贡献表述与实施范围

FRAMe已使用精确场景匹配后再做语义排序，并有几何有效性检查，因此“先过滤再检索”或“加校验”不能直接被称作首创。[FRAMe §2.2–2.3](https://arxiv.org/html/2607.06964v1)

本研究可以检验的更具体增量是：小模型指令转换在任务状态/规则版本变化下的可靠性，以及有限错误反馈能否在保留用户要求的同时改善输出。仍需进一步近邻核查与实测后才能确定创新性。暂定题名可调整为《面向无人机任务转换的状态约束检索与验证反馈修正方法》。

实施顺序：规则条目与离线标注 → 固定模型的全量提示/普通检索基线 → 状态约束检索 → 结构化校验与一次反馈修复 → 执行前版本/状态复核 → AirSim正式对照。当前建议涉及固定地图已知目标；自然语言指定未知视觉目标、双机协同和新的轨迹优化方法不进入第一版范围。
