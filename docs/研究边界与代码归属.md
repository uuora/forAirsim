# 两条交付线的边界与代码归属

编制：2026-09-17。目的：同一个 AirSim 工程要同时支撑两份独立交付，本文件记录哪部分代码、配置和运行产物属于哪一份，避免两篇论文的结论互相污染。

本文件是**约定**，不是已验收事实；模块归属依据各文件 docstring 和开发日志核查得出，若后续拆分或改名需要同步更新本表。

## 1. 两条交付线

| | 线 A | 线 B |
|---|---|---|
| 交付 | 老师投稿的论文 | 本人毕业论文 |
| 任务 | 双无人机气球碰撞/接触 | 海上搜救 |
| 候选题目 | 《面向气球接触任务的双无人机感知可靠性判别与自适应接替方法》 | 《面向海上搜救的轻量化语言智能体与自适应检索增强方法研究》 |

| 主要指标 | 接替判定正确性、失败识别时机、对照固定超时策略 | 任务正确性、端到端延迟、证据引用完整性 |

## 5. 分支与提交约定

**不要开两条长期分支。** 理由：共享底座里的 `configs/settings.json`、`onboard_sensors.py`、`check_onboard_sensors.py` 和几份文档会被两条线同时改，长期分叉后合并全是冲突；而且两条线是同一条 AirSim 平台演进路径，没有独立分支的必要。

约定：

- `main` 是唯一主干，始终保持可运行
- 每个工作单元开一条**短分支**，做完合回，分支名带归属前缀：
  - `balloon/…` 线 A
  - `thesis/…` 线 B
  - `shared/…` 或 `chore/…` 共享底座与杂务
  - `docs/…` 纯文档
- 提交信息里同样带前缀，便于以后按线筛 `git log`

边界靠**文档和命名**表达，不靠分支。

## 7. 已知污染点

1. **`python/language_plan.py:51` 仍输出气球任务步骤**（`A_visual_alignment` / `A_visual_range`），没有任何海事任务意图。线 B 的方法层目前挂在被替换掉的线 A 任务上，继续开发前需要先解耦。
2. **`configs/settings.json` 同时服务两个场景**，任一线改传感器配置都要确认另一条线仍能启动。
3. **`docs/development-log.md` 按日期混记两线**，此后新条目建议标注线别。
4. **`docs/` 下两份文档对"当前主线"的表述不一致**：`research-plan-20260913/从当前进度到论文发表_执行路线.md`（09-13）写气球任务，`海上搜救Agent_平台与研究范围决策.md`（09-14）写语言智能体。本文件以"两条并行、互不替代"为准，但两位交付对象（老师、本人）各自的时间要求仍需确认。
